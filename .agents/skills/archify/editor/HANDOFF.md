# archify 요소 편집기 — Hand-off 문서

이 문서는 `archify/editor/`(archify 다이어그램 스킬 위에 얹은 "요소 단위 AI 에디터")를
이어받는 사람(미래의 나 자신 포함)을 위한 진입점이다. 전체 설계·결정 이력(D1~D45,
매 결정의 WHY/COST/EXIT)은 같은 디렉토리의 `DECISIONS.md`에 있다 — 이 문서는 그
요약 + 실무 안내다.

## 이게 뭔가

archify가 만드는 다이어그램(JSON 기반, `archify serve`로 재렌더)과, 손으로 만든
HTML 슬라이드(div 레이아웃 또는 인라인 `<svg>` 하나짜리) 둘 다를 열어서, **요소
하나를 클릭 → 그 요소만 편집**할 수 있게 하는 웹 앱이다. 텍스트 직접 수정, 서식
(폰트/크기/굵기/정렬/색), 도형 채움/테두리, 화살표 CAD 편집, 이미지/표/링크 삽입,
다중선택 일괄편집·이동·겹침순서, undo/redo, LLM(NVIDIA Build) 기반 "이 요소를
이렇게 바꿔줘" 자연어 편집을 지원한다.

## 핵심 아키텍처 — 반드시 지켜야 하는 불변식

**요소 단위 스코프 보장(3계층)**: 이 프로젝트의 모든 편집 기능이 지켜야 하는
단일 원칙이다.
1. **스키마 pin** — LLM 응답이든 직접조작이든, 대상 eid를 스키마 레벨에서
   `{"const": eid}`(단일) 또는 `{"enum": [...]}`(다중선택)로 고정해 범위 밖
   생성을 원천 차단.
2. **apply-time scope-gate** — 적용 시점에 대상이 선언한 스코프를 벗어나면
   `ScopeViolation`.
3. **post-apply `bleedDiff`** — 적용 전/후 문서를 diff해서 **허용 집합 밖은
   byte-identical**임을 실증. `dom-adapter.js`의 `bleedDiff`는 4개 모드:
   `"replace"`(기본, 단일/다중 eid 둘 다), `"remove"`/`"add"`(삭제·붙여넣기),
   `"reorder"`(z-order). 새 기능을 추가할 때 이 중 맞는 모드를 재사용하거나,
   정말 안 맞으면 같은 원칙으로 새 모드를 additive하게 추가한다(기존 모드를
   바꾸지 않는다).

**4종 addressable 유닛**: `svgbox:N`/`svgtext:N`/`svgedge:N`(순수 SVG, DOM
순서로 페인트) vs `obj:N`(진짜 HTML `<div>`, 실제 CSS z-index 있음). 새로
"그리는" 요소(＋텍스트상자/도형/이미지/표)는 **문서가 어느 클래스든 항상
obj로 삽입된다**(`dom-adapter.js:addObject`) — SVG DOM은 절대 직접 안 건드림.

**3개 provenance 클래스**: (a) archify-JSON 기반(서버 재렌더 필요, 서식툴바
전체 비활성 — JSON 재렌더가 DOM 서식을 지움), (b) div-per-요소 손제작 슬라이드,
(c) 인라인 SVG 하나짜리 손제작 슬라이드(박스 `<g>` stamping + 자유텍스트
`svgtext:N` 별도 주소화).

**요소편집 ON/OFF 토글**: ON=블록편집(드래그/리사이즈/채움/테두리, 텍스트직접
편집 불가), OFF=텍스트편집(클릭 즉시 인라인편집) — 단 유닛 테두리 클릭은 OFF
상태에서도 이동 드래그를 무장(예외).

## 이 프로젝트에서 작업을 이어가는 방법 (이 세션에서 검증된 패턴)

D17부터 D44까지 전부 이 4단계 루프로 진행했고, 매번 실제 버그를 잡아냈다 —
생략하지 말 것:

1. **버그 신고면 재현부터, 짐작 금지.** 라이브(Playwright, mock 경로 — LLM
   불필요한 직접조작 기능이 대부분)로 재현하고 근본원인을 코드 위치까지
   확정한 뒤에만 수정 방향을 정한다. 재현 안 되면 "버그 아님"으로 정직하게
   보고하고 코드를 건드리지 않는다(이 세션에서 실제로 2건 그랬음 — 링크버튼,
   Option+클릭).
2. **결정은 D-번호로 `DECISIONS.md`에 WHY/COST/EXIT와 함께 기록.** 애매한
   지점(구현이 여러 방향으로 갈릴 수 있는 지점)은 사용자에게 명확한 선택지로
   묻는다 — 이 세션에서 두 번 실제로 사용자의 답이 "권장안(현행유지)"이 아니라
   "확장" 쪽이었다(D43/D44), 짐작으로 넘어갔으면 틀렸을 것.
3. **구현은 정밀한 브리핑과 함께 새 에이전트에 위임.** 브리핑엔 파일:줄번호
   레벨의 그라운딩(사전 조사한 근거 코드 위치)을 반드시 포함 — "이해했다는 걸
   증명하는" 브리핑이어야 한다. "될 것 같다"는 표현을 브리핑에도 보고에도
   금지시킨다. 임의 숫자(반경/임계값/하한 등) 신설 금지 — 기존 상수 재사용
   또는 실측 근거를 요구한다.
4. **완료 보고를 절대 그대로 믿지 않는다.** 반드시 별도 세션(fork)으로
   독립 검증: git diff 직접 읽기, 풀회귀 처음부터 재실행(재사용 카운트 금지),
   라이브 재현 직접 재구성(에이전트의 스크린샷/설명 재인용 금지), 특히 보안
   관련(sanitizer)이나 "테스트를 수정했다"는 보고는 회귀 은폐 여부를 diff로
   직접 판정. 이 세션에서 자기수정(에이전트가 스스로 낸 회귀를 스스로 발견)과
   정당한 테스트 오라클 수정(회귀 은폐 아님)을 각각 실제로 겪었다 — 둘 다
   가능하므로 매번 실측으로 구별해야 한다.
